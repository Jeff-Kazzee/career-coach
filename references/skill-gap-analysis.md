# Skill-Gap and Proof-Gap Analysis

## What this reference is for

Compare a user's current capabilities and evidence with a target role, identify the smallest high-value gap, and design practice plus a credible proof artifact.

## When the agent should read it

Read this for Skill-Gap Analysis, Career Change Mode, learning-plan design, portfolio planning, credential decisions, or when the user keeps taking courses without becoming more competitive.

## The concrete process

### 1. Define the target narrowly enough to compare

Specify:

- Role family and level
- Industry or domain when it changes requirements
- Geography and work mode
- Employment path: job, contract, freelance, apprenticeship, open source, creator, or hybrid
- Time horizon

Do not merge junior and senior requirements or several unrelated roles into one gap list.

### 2. Build the requirement set from current evidence

Use authoritative occupation sources for broad task and skill definitions, then current postings or client briefs for actual target-market language.

Classify each requirement:

- **Common:** appears repeatedly and is central to the work.
- **Preferred:** useful but not consistently required.
- **Employer-specific:** tied to one environment or stack.
- **Gate:** license, credential, clearance, location, physical condition, or authorization that cannot be replaced by a project.
- **Uncertain:** sample too small or wording ambiguous.

Do not promote a fashionable tool to “required” because it appeared once.

### 3. Audit current capability and proof separately

For each requirement, record:

| Requirement | Ability | Recency | Existing proof | Proof quality | Gap type |
|---|---:|---|---|---:|---|

Use 0–3 for local comparison:

- `0` no evidence or unknown
- `1` basic exposure
- `2` can perform with realistic support
- `3` can perform independently at the target level with current evidence

Gap types:

- **Knowledge gap:** concepts are missing.
- **Performance gap:** knowledge exists, but realistic execution is weak.
- **Proof gap:** capability exists, but outsiders cannot verify it.
- **Signal gap:** proof exists, but the resume/profile does not surface it.
- **Recency gap:** skill has not been used recently enough for confidence.
- **Access gap:** equipment, software, data, mentoring, transport, schedule, or accommodation blocks practice.
- **Gate:** a formal requirement needs separate research.

### 4. Prioritize without false precision

Rate each gap as low, medium, or high on:

- Frequency in target opportunities
- Importance to actual work
- Severity of the user's gap
- Ability to create credible proof soon
- Cost in time, money, energy, and access
- Reusability across adjacent roles

Select the gap with the strongest combination of market value, proofability, and feasibility. Explain tradeoffs. Do not present an arbitrary decimal score as scientific.

### 5. Decide whether learning is actually needed

Use this order:

1. Surface existing proof.
2. Improve or reframe an existing project.
3. Complete a targeted practice task.
4. Build a small realistic project.
5. Seek feedback or supervised practice.
6. Take a focused course or credential only when it closes a real gap.

A course is not proof unless it includes assessed work that the user can honestly explain and, where allowed, show.

### 6. Design the fastest credible project

A good bridge project has:

- A target user or stakeholder
- A realistic problem
- Constraints resembling the role
- A defined artifact
- A quality check
- A feedback source
- A short enough scope to finish
- A public or sanitized explanation when the work itself cannot be shared

Project brief:

```markdown
Problem:
Target user:
Target requirement proved:
Constraints:
Artifact:
Definition of done:
Validation:
Evidence to publish:
Time/energy budget:
```

Avoid toy projects when a small real contribution is accessible. Also avoid unpaid production work disguised as a “portfolio opportunity.”

### 7. Define the minimum viable portfolio artifact

Possible artifacts include:

- Case study
- Demo and README
- Analysis with reproducible method
- Design rationale
- Troubleshooting guide
- Process improvement proposal
- Test plan
- Tutorial based on verified work
- Open-source contribution
- Before/after workflow with evidence
- Client-style deliverable using synthetic or public data

The artifact must state the user's role, decisions, limitations, and evidence. Never publish confidential data or copy an employer's proprietary work.

### 8. Build a deliberate practice plan

Each practice block should contain:

1. Target subskill
2. Task just beyond current reliable performance
3. Observable output
4. Feedback or test
5. Revision
6. Evidence logged

Example:

> Twice weekly, debug one intentionally broken small application under a 45-minute limit. Record hypothesis, tests, root cause, fix, and prevention. Review against a rubric and publish one sanitized case study after four attempts.

Use minimum, standard, and stretch versions for variable energy.

### 9. Evaluate credentials carefully

Before recommending a certificate, degree, bootcamp, or license, check:

- Is it legally required, commonly requested, or merely advertised?
- Do target employers name it?
- Does it produce assessed work or access to hiring channels?
- Total cost, time, accessibility, and debt risk
- Completion and placement evidence from reliable sources
- Opportunity cost versus projects, experience, or targeted applications
- Expiration or continuing-education requirements

For regulated careers, use the responsible licensing authority. Do not improvise eligibility advice.

### 10. Set a reassessment rule

Examples:

- After the artifact is reviewed by two qualified people
- After five target-aligned applications use the new proof
- After four practice attempts show no improvement
- After current posting research changes the requirement map

The plan should stop or change when evidence contradicts the original hypothesis.
